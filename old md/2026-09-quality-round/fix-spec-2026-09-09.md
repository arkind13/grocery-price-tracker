### FIX-1 (defect D6): UOM size gate is bypassed on sheet+live pairs
**User impact:** "Sunbites Sour 60g" (sheet, WW cell = GONE) was compared
against a live Woolworths 110g product and the Coles 60g sheet price — a 60g
vs 110g pair that the 20% band must reject. User hit this class LAST
Wednesday too and was told it was fixed; that fix evidently covered only
live↔live pairs. This one is the mixed-provenance path.

**Root cause location:** `core/uom.py` implements the gate and
`core/lookup.py::select_live_pair` applies it to live-live pairs. The
compare/`auto` comparator (`core/price_comparator.py`, sheet-side with a
live fallback for the OTHER store — and the GONE/blank-cell live fallback)
pairs a sheet row with a live product WITHOUT calling the gate.
Evidence: `data/test_logs/2026-09-08-comprehensive/outputs/T1.V09*.txt`
(item 3: "Sunbites Sour 60g · 110g", WW live vs Coles sheet).

**Fix:**
1. Find every place `price_comparator.py` (and the lookup engine's
   live-fallback step) builds a pair where at least one side comes from the
   sheet: route BOTH sizes through `core/uom.py::comparable` (sheet side
   uses Col C; live side uses the parsed PackageSize). No pair, no totals —
   render the found-block instead.
2. **GONE semantics:** a cell holding `GONE` means the user verified the
   product unavailable at that store. Live fallback for a GONE side must
   either (a) be disabled entirely, or (b) only answer when the live result
   is the SAME product per `name_matcher.is_same_product` AND passes the UOM
   gate — never silently substitute a different size/product.
3. Never pair across provenance without the gate even when both sides share
   a brand word.

**Acceptance:**
- `compare --items "Sunbites Sour 60g"` shows NO WW-live/Coles-sheet pair at
  110g vs 60g; a found-block or per-store note instead.
- New regression tests: mixed pair 60g/110g rejected; mixed pair 60g/70g
  (within 20%) allowed; GONE cell + same-product live result behaves per
  chosen (a)/(b); GONE cell + different product never pairs.

### FIX-3 (defect D1): multi-buy rate divided twice in local-deals ingest
**User impact:** "2 for $2.99" written as 0.75 instead of 1.50 into the
Local_Deals tab, and the comment reads "[multi buy 2 for $1.50 — $0.75/ea]"
(bundle total itself already divided).

**Root cause:** `extractors/deal_text.py` line ~91 already returns the
PER-UNIT rate (`"price": round(bundle / qty, 2)`, docstring line ~124:
"Price is per-unit"). `core/local_deals.py::_cell_for` (~line 1293) divides
AGAIN when `price_kind == "multibuy"` via
`core/multibuy.py::effective_unit_rate`. The image/vision parser's price
contract must be checked before changing either side — the two parsers must
agree on ONE convention.

**Fix (single-owner principle):** make the parser the only place that
knows the convention and document it in one place:
- Recommended: parsers return the BUNDLE TOTAL plus `multibuy_qty`, and
  `_cell_for` is the ONLY divider (one `effective_unit_rate` call).
  Audit `deal_text.py` AND the vision parser path (`extractors/fb_flyer_fetch.py`
  / wherever `price_kind` is set) and convert both to the same convention.
- Whatever convention you pick, fix `_multibuy_note` (~line 1277) so the
  note shows the true bundle ("multi buy 2 for $2.99 — $1.50/ea").

**Acceptance:**
- Real FRUT anniversary text through the parser + tab write → Celery and
  Carrots cells = 1.50 (not 0.75), note = "[multi buy 2 for $2.99 — $1.50/ea]".
- Regression tests for both parsers: "2 for $2.99", "Any 2 | $6.00",
  bulk packs ("10kg box $55") — cell and note both correct.
- `grep -n "effective_unit_rate" core/ extractors/` — the divide must be
  reachable from exactly ONE call path per deal.

### FIX-4 (defect D2 + D11): freshness gate on ingest + comments must expire WITH their prices
**User impact:** an FB board whose deals ended 6 Sep was fully written on
8 Sep; and when a newer post re-prices an item without the promo, the old
"[multi buy …]" comment stays on the sheet forever. User requirement
(2026-09-09): **when a special price is removed/expires, its shop-tagged
comment is removed with it.**

**Root cause:** the ingest path (`local-deals --ingest`, merge via
`core/local_deals.py::merge_store_tab` / `build_rows`) never checks the
parsed validity end-date, and comment segments are unioned per shop instead
of being rebuilt per post.

**Fix:**
1. In ingest: if a file's parsed validity end-date < today (Sydney) → write
   NOTHING to the tab; print "deals ended <date> — nothing written" and
   record the post in the post log with an `expired: true` flag. (Undated
   boards keep today's behavior.)
2. Comment lifecycle: each item's Comments cell is rebuilt from the
   NEWEST post per shop per item — segments from older posts that no
   longer appear (or whose promo is gone) are dropped. A plain price with
   no note must leave the comment EMPTY, not keep the last promo text.
3. `--expire-sweep` additionally clears the shop-tagged comment segment of
   any special cell it removes (currently it clears only the price cell +
   row-2 stamp).

**Acceptance:**
- Re-ingest of the expired FRUT board writes 0 cells and says so.
- Carrots re-priced plain → `[multi buy …]` segment gone from Comments.
- Sweep removes price AND its comment segment.
- Regression tests for all three; existing local-deals tests stay green.

### FIX-5 (defect D3): cross-store add in `map unmatched --add`
**User impact (user: "I have faced this a lot"):** a debt entry tagged
`[coles]` was resolved with `--add` while Coles was unavailable; the flow
live-searched WOOLWORTHS, added the Woolworths product into the Woolworths
price column, and queued a WOOLWORTHS to-do entry — for a COLES list line.
Silent wrong-store data, every time one store is down.

**Root cause:** the unmatched resolve session (`grocery_price_cli.py`,
map handlers) delegates `--add` to the lookup engine's live step, which
searches BOTH stores and takes the best hit, ignoring the debt entry's
`[store]` tag. The shop flow had this exact bug fixed on 2026-09-07
("never borrow across stores" — checker defect #4); the map path never
got the same treatment.

**Fix (mirror the shop-flow rule, one store, no fallback):**
1. The resolve session for a `[<store>]`-tagged debt item searches ONLY
   that store. Thread the store tag into the live-search call.
2. If that store is unavailable (Scrape.do breaker open, HTTP failures,
   empty result is NOT unavailable — empty means "not listed"), do NOT
   touch the other store. Print: "⚠️ <store> unavailable right now — item
   left on the list. Try again later, or reply with the exact product name
   / keyword." and leave the debt entry + session position intact.
3. `--keyword NAME` on a tagged item writes the keyword into THAT store's
   keyword column only (assert this while you're in there).
4. Same rule for `map wool` / `map coles` sessions (they're already
   store-scoped — verify, don't assume).

**Acceptance:**
- Regression test: coles-tagged debt entry + mocked broken Coles + healthy
  Woolworths → no sheet write, no to-do entry, honest message, debt intact.
- Healthy Coles → add works, price into Col E, to-do entry store = coles.
- Live check on the real sheet: repeat the Yallamundi scenario from
  outputs/T4.U05 with Coles healthy.

### FIX-6 (defect D7 + user's sugar case): halal chain + wrong-product partial matches on ALL answer surfaces
**User impact:** `compare "chicken breast"` answered with "Jumpy's Chicken
Multipack" (potato chips, sub-category `chicken chips`). Same class
yesterday: a **sugar** query answered with the **V Sugarfree / Red Bull
Sugar Free** drink rows. Two distinct failures:
  a) the halal-scoped resolution chain is only wired into shop/optimize —
     compare/recipe never engage it;
  b) the partial-match scorer lets a query through on substring/generic
     token overlaps with no floor.

**Root cause:** `core/lookup.py::find_product` has `_halal_chain` and
`_halal_scoped_index` but they are invoked only from the halal resolution
entry points; `compare`'s `_gather_lookup_prices` (price_comparator.py)
calls find_product WITHOUT the chain. The candidate scorer (Step 3 partial)
has no boundary guard — the word-boundary safety rules exist only in
`core/subcategory.py` (e.g. "V Sugarfree" is not sugar, "eggplant" is not
eggs).

**Fix:**
1. Wire the halal chain into every user-facing answer path: compare,
   recipe, optimize's substitute step (grep for
   `find_product(` call sites; if the query `is_meat_term(...)` per
   `core/halal.py`, route through the halal chain — sheet halal view →
   live halal tier → Local_Deals butcher tier → honest "not available
   this week").
2. Add a **boundary/crossing guard to lookup candidate scoring** (port the
   rule from `core/subcategory.py`): if the query's distinguishing token
   appears only as a SUBSTRING of a candidate token ("sugar" ⊂ "sugarfree"),
   the candidate is excluded from auto-selection (it may still be shown in
   interactive candidate lists, labelled, but never auto-picked, never
   priced silently).
3. Auto-pick floor (pairs with FIX-7): a partial candidate auto-picked by
   compare must share at least one MEANINGFUL token (non-generic, non-size,
   non-brand-prefix) with the query AND not violate the boundary guard.
   Otherwise: not-found → found-block.

**Acceptance:**
- `compare --items "chicken breast"` → no chips row; halal chain output or
  honest not-available.
- `compare --items "sugar"` → RAW SUGAR rows or a question — NEVER
  "Red Bull Sugar Free" / "V Sugarfree" (regression test with the real
  row names from the sheet dump).
- `compare --items "eggplant"`-style boundary cases stay correct.
- All existing lookup/subcategory/halal tests green.

### FIX-7 (defect D5): no silent pricing of nonsense/low-confidence queries
**User impact:** `compare --items "xyzzy plugh quantum banana 999"` returned
a full price battle from row "Banana Kids 5" (single shared word "banana")
and counted it in totals.

**Root cause:** compare/auto mode's Step 3 auto-picks the top partial
candidate with no score floor (`find_product(interactive=False)`).

**Fix:** implement the auto-pick floor from FIX-6 point 3 as a named
constant (e.g. `AUTO_PICK_MIN_SCORE` in lookup.py) so it's tunable in one
place. Below the floor: LookupStatus.NOT_FOUND → the comparator renders
the found-block ("looked at both stores, couldn't price") + the add-item
hint. Nonsense queries must NEVER reach totals.

**Acceptance:**
- The junk query from outputs/T1.V07 renders a found-block, no totals.
- Real fuzzy-but-legit queries still work (e.g. "milkk" → milk rows or an
  explicit question — decide: auto-answer still allowed for close matches
  above the floor).
- Regression tests: shared-word-only query rejected; 2+ meaningful-token
  matches still auto-priced.

the refused item's OWN future row — and the sheet ended with MORE rows than

### FIX-10 (defect D17): make the variant behavior consistent

refusal ("already tracked", no price/alias update) and the one-line-rule
merge (price+alias update), depending on which guard sees the name first.
Pick ONE documented behavior: recommended — the exact-guard's normalize
should NOT be order-insensitive (exact means EXACT); reordered names go to
the one-line rule and MERGE (price + alias). Add tests for both forms.
